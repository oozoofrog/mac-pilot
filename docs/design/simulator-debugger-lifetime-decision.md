# Simulator debugger lifetime decision

2026-11-09 · Independent, headless decision preparation. **Next experiment: one resident, externally compiled Simulator helper, with a stable main-queue callback and cooperative cancellation.** Keep general capture/edit gates disabled. Public LLDB checkpoint restoration does not guarantee language cleanup after interruption. This note changes no production behavior or qualification requirement.

## Why a real catch is necessary but insufficient

The current `SetTrapExceptions(True)` path stops at a throw before a compiled catch can run. The pinned [LLDB exception-breakpoint implementation](https://github.com/llvm/llvm-project/blob/27e76c830b95b1f67836df024d860a5deff35405/lldb/source/Plugins/LanguageRuntime/ObjC/AppleObjCRuntime/AppleObjCRuntime.cpp) requests a throw breakpoint; [call-plan restoration](https://github.com/llvm/llvm-project/blob/27e76c830b95b1f67836df024d860a5deff35405/lldb/source/Target/ThreadPlanCallFunction.cpp) restores a checkpoint. Merely compiling a dylib catch while retaining that synchronous trapped execution path is insufficient.

[Clang's pool semantics](https://clang.llvm.org/docs/AutomaticReferenceCounting.html#autoreleasepool) also matter: an exception escaping a pool block does not drain it. Use `@autoreleasepool { @try { finite work } @catch (id e) { fixed failure state } }`, so the helper catches inside its pool and exits that pool normally. Publish cleanup completion only afterward. Catching outside the pool is the wrong shape. If helper-owned ARC code is introduced, qualify its exception cleanup flags separately; it cannot repair the app's own unbalanced MRC ownership or ARC code compiled without exception cleanup.

| Mechanism | Useful guarantee | Remaining defect/cost |
|---|---|---|
| Current direct expression, including removing its pool or adding option strings | Existing successful-return behavior | Neither exception codegen nor interruption cleanup is repaired. Reject as the next lifetime fix. |
| Compiled helper called synchronously by LLDB; trap disabled; cancellation deferred | Real catch and normal pool exit when work returns | The host remains coupled to the injected frame. Timeout/forced unwind still skips cleanup; an unbounded setter defeats a finite wait. Smaller patch, insufficient execution mechanism. |
| **Resident compiled helper; main-queue callback after LLDB submission returns** | Normal callback return/catch can drain its owned pool even after the host stops waiting | Requires a bounded request/receipt channel and persistent image ownership. Cannot bound arbitrary app execution or promise target recovery. Recommended discriminating experiment. |

## Smallest workable design candidate

1. Build a fixed C-entry Objective-C helper against the selected Apple Simulator SDK, with explicit MRC and `-fobjc-exceptions`. Keep it free of custom `+load` hooks and app SDK integration. Sign normally and load only into an owned, authorized, debuggable app through the supported debugger image-load route. [SBProcess.LoadImage](https://lldb.llvm.org/python_api/lldb.SBProcess.html#lldb.SBProcess.LoadImage) is a candidate public API, not verified guest capability here. Refuse unsupported architecture, signing, sandbox/path or loader conditions. No entitlement change, re-signing of the target or security bypass.
2. Pin exactly one known helper image for that target lifetime. Retain its load handle; do not unload at inspection close. Use `dispatch_async_f` with a function in that image and bounded module-owned context. No callback, block invoke pointer, string pointer or stack data may escape from LLDB JIT storage. Check owner/epoch/schema/module identity before reuse; do not accumulate versioned images. This introduces an explicit, bounded resident-image cost that the current no-persistent-callback design does not have.
3. Use LLDB only for bootstrap and a short fixed submission, never for traversal/getter/setter/texture execution. Submission copies a capped request into one module-owned slot and queues at most one callback. Use only fixed operations, never caller-supplied code or function pointers. Keep the existing durable operation reservation, digest, sequence fence and target ownership. Ambiguous load/submission still quarantines; it does not permit another load or replay.
4. On the normal main queue, revalidate authority, expiry and cancellation, then perform the existing weak-identity/graph/value checks and at most one setter. The callback owns a local pool with its catch inside. Check cancellation before entry and after finite critical execution. Between entry and completion, never interrupt or forcibly unwind the callback. A small protected per-operation cancellation marker can be read at these boundaries; no polling target timer or second target cleanup injection is needed. The actual UIKit main-thread condition must be observed in the guest experiment; this console control does not prove it.
5. Stage the fixed result while inside the pool; publish terminal cleanup evidence after normal pool exit through bounded owned bytes. Retain only the capped registry/receipt/tombstone required by the existing contract. No persistent selected-view reference. Clear busy only through the callback's verified completion transition, never in response to a host deadline. A publication failure or abnormal drain keeps cleanup unknown. The request slot and image must remain valid until the callback has returned, even if host UI closes.
6. Detach the debugger independently. Host cancellation revokes authority and ends waiting within the existing host/cleanup budgets. It does not assert that queued work was removed or an entered setter stopped. Cancellation before the callback's entry check can produce a verified no-entry result. A later cancellation may follow one applied write; keep its eventual target receipt separate from the host cancellation record. A caught throw after entry remains uncertain and provides no undo. A late normal readback may document `appliedObserved`, but must not silently restore the cancelled inspection's authority or permit replay.

For the first experiment, existing bounded private files are sufficient for request/receipt/cancellation transport; a new general RPC service is unnecessary. Production integration must preserve the existing ownership, byte caps and publication rules. Submit on the stopped main thread; keep it stopped after the expression returns until detach resumes it. If the debugger is still attached when a callback runs, its exception traps/stops can defeat the intended execution context: prove untraced callback entry after submission return and actual detach, with independent host recovery readback, or stop. The callback may start before host readback completes. Do not pump the run loop in an expression.

## Guarantees that remain impossible

An overridden getter, setter, drawing method, destructor, KVO hook or swizzled implementation can hang, abort, corrupt memory or produce unrelated effects. A real catch only handles supported language exceptions that reach it; it is not a transaction or crash boundary. Even a system-image setter can call app hooks. A pool drain itself can execute app destructors. No public LLDB option establishes safe asynchronous forced unwind of arbitrary code.

Therefore **bounded host cancellation and bounded target completion/recovery are different promises**. If target work never returns, report `pending/uncertain`, revoke authority, preserve the in-flight slot/busy state and stop admission. Do not claim memory release or a responsive app. Restart/termination is a separately authorized recovery action that loses app state, not successful cleanup. Do not reset busy, pop an unknown pool, replay an uncertain setter, synthesize rollback or unload pending code.

Method-implementation qualification/refusal is necessary before expanding beyond the owned finite fixture. Cover getters/traversal/drawing as well as setters; reject unqualified overrides, forwarding/swizzling and unsupported runtime combinations. IMP/image checks can support that policy but cannot prove termination or absence of transitive hooks. A defensible product scope is a qualified, cooperative debug-app inspection/edit operation with explicit uncertainty and recovery limits. If unchanged requirements demand arbitrary current-app execution plus guaranteed finite target recovery and complete cleanup, this mechanism cannot satisfy them; keep the gates disabled. No requirement is waived by this decision.

## Discriminating experiment and evidence

Completed here, without a guest: the full canonical expression parses under selected LLDB; option probes fail to enable `@try`; the Apple binary's restoration path was disassembled without a process. A standalone Foundation CLI loads a stable dylib and runs normal, throw-after-write, finite post-entry cancellation and pre-entry cancellation controls on a serial main queue. **31 assertions pass**: one write and sentinel deallocation/weak nil after normal or caught execution; the finite cancelled action actually returns; pre-entry cancellation produces zero writes. Completion observes the pool already exited. The helper remains loaded until process exit. This is language-lifetime evidence, not LLDB attach, UIKit, signing-admission or Simulator proof.

The same helper builds as an arm64 Simulator dylib and passes ad-hoc signature verification. Mach-O platform is iOS Simulator, minimum/SDK 27.2. Its IR contains `__objc_personality_v0`, `invoke`, an Objective-C landing pad/catch, and a common normal `autoreleasePoolPop` before completion. No Simulator executable or dylib was run or loaded.

**Next executable step for the runtime owner:** adapt only this resident-callback boundary to the existing owned A/B fixture. Reuse its protected session, source freeze, input guards, sentinel oracle and recovery checks. Use two fresh lifetimes: (A) one throw after one write; (B) cancellation after the existing finite setter entry. Do not rerun the full ten-operation sequence to choose the mechanism.

Accept this mechanism experiment only if both lifetimes establish:

- The exact helper hash/UUID/platform is loaded once; callback PC belongs to that image, and untraced entry occurs on the normal UIKit main thread after actual debugger detach, independently confirmed by host recovery readback. No app SDK helper or escaped JIT callback executes the operation.
- A catches inside the pool, records one write and an uncertain/no-undo receipt, then releases its sentinel. B records host cancellation promptly, lets the finite setter return once, drains its pool and records the late target outcome without restoring authority. Sentinels deallocate and the weak target can clear after its final fixture reference is removed, before any ambient-pool assumption is used.
- Receipt ordering distinguishes accepted, entered, callback work finished, pool exited and terminal publication. Retained-receipt replay/old-authority refusal dispatches zero setters. Record callback/request ownership and remaining bounded registry/receipt/image bytes; no operation-owned view or callback context remains after completion. The resident image is an explicit lifetime cost, not zero memory.
- Existing limits suffice. The same app lifetime is running/untraced and responsive afterward, debugger children are reaped, exact owned fixture state is cleaned, and unrelated processes remain untouched.

**Stop** on loader/submission uncertainty, callback entry before safe detach, exception interception, deadline overrun without terminal target evidence, extra setters, missing deallocation/weak clearing, residual owned context, or failed recovery. Preserve uncertainty and disable the route. Do not use another injected cleanup, retry, forced unwind or longer arbitrary timeout to manufacture acceptance. Passing this pair selects a lifetime mechanism only; it does not qualify arbitrary apps, nonreturning setters, all texture paths or host 3D/LCD UI.
