# Xcode View Debugger: inspection and runtime-edit research

Research only, 2026-11-09. Scope: static repository and installed-tool inspection, public documentation and original project source. No GUI, target attach, runtime API invocation, simulator mutation, or installation was performed. Local binary observations below refer only to selected Xcode 27.2 (27B48) and macOS 27.2 (26B123); they are not an Apple API contract or a proof that a particular simulator runtime supports the operation.

## Decision inputs

A coherent first inspector can combine a fresh, identity-bound UIKit hierarchy capture with an independent native 3D window, synchronized tree/selection/property panes, explicit refresh and a narrow typed edit operation. Its 3D planes must represent **captured visual layers**, not just a screenshot projected onto every node. The current collector has neither per-node textures nor a general-app support proof; therefore a faithful textured inspector and safe edits are **not yet implementable as proven capabilities**. Start with gated experiments below. An outline-only 3D prototype can test UI mechanics but cannot satisfy the requested displayed composition by itself.

Xcode's documented view debugger displays a snapshot of the paused app, with an exploded 3D view, hierarchy, object/size inspectors and constraints; users can rotate and change spacing. Apple documents attaching, navigating and inspecting, and separately documents changing variables through the LLDB console. The cited sources do **not** establish that Xcode's view inspector itself writes view properties. Its debugger console is not evidence of a view-inspector setter. See [Apple's workflow](https://developer.apple.com/documentation/xcode/diagnosing-issues-in-the-appearance-of-your-running-app/), [view-debugger help](https://help.apple.com/xcode/mac/current/en.lproj/dev4dfdedb7a.html), and [LLDB console workflow](https://developer.apple.com/documentation/xcode/stepping-through-code-and-inspecting-variables-to-isolate-bugs). WWDC19 describes a richer mixed UIKit/SwiftUI inspector using Swift reflection and modifiers ([session](https://developer.apple.com/videos/play/wwdc2019/412/)); ordinary UIKit backing views do not reconstruct that declarative graph, its data flow, or source code.

## Current implementation and provenance

- [`capture.py`](../../mac-computer-use/skills/mac-computer-use/scripts/view-capture/capture.py) builds a JSON dictionary, base64-encodes it and embeds it in [`collect.expr`](../../mac-computer-use/skills/mac-computer-use/scripts/view-capture/collect.expr). After `dlopen("/usr/lib/libViewDebuggerSupport.dylib", 2)`, the expression resolves `DBGTargetHub`, calls `sharedHub` and `performRequestWithRequestInBase64:`, and parses the returned bytes as JSON. The request has UUID `DBGHierarchyRequestIdentifier`, initiator version 4, priority 0, no transport compression, object discovery 1, and one `DebugHierarchyPropertyAction` with visibility 1 and `propertyNamesAreExclusive: false`. Its explicit names are `frame`, `bounds`, `center`, `transform`, `clipsToBounds`, `hidden`, `alpha`, `accessibilityIdentifier`, `accessibilityLabel`, `text`, `firstItem`, `firstAttribute`, `relation`, `secondItem`, `secondAttribute`, `multiplier`, `constant`, `priority`, `active`, `identifier`. Requested does not mean returned; non-exclusive does not establish a complete property set.
- The response is checked for `hierarchy.topLevelGroups`; [`SimulatorViewHierarchy.swift`](../../mac-computer-use/skills/mac-computer-use/scripts/mac-cu-src/SimulatorViewHierarchy.swift) expects group `com.apple.UIKit.UIWindow`, `debugHierarchyObjects`, node `objectID`, `className`, `properties` containing `propertyName`/`propertyValue`, and recursive `childGroup.debugHierarchyObjects`. It preserves sibling enumeration order and raw properties, but extracts only frame, hidden, alpha and accessibility strings into typed fields. Missing and malformed fields are not equivalent to an empty hierarchy. This is an observed repository schema, not a published schema or proof of all Xcode response variants.
- The same expression walks actual window/subview objects separately, obtains bounds corners by converting through the window to `UIScreen.fixedCoordinateSpace`, and joins using exact object-address strings within the capture. The envelope explicitly contains `screenshot: null`; it sets `verified=false`, `overlayEnabled=false`, and clipping unverified. Traversal is bounded at 20,000 views, serialized JSON at 16 MiB, and conversion at 100,000 nodes/512 depth. These sequential observations are not an atomic screen frame. Existing fixture evidence reports 14 exact hierarchy/geometry joins and seven independent corner comparisons with zero error for one static portrait fixture. It does not prove general-app capture, texture fidelity, rendered LCD alignment, clipping, 3D, or mutation. See [capture evidence](../simulator-view-capture.md).
- [`SimulatorViews.swift`](../../mac-computer-use/skills/mac-computer-use/scripts/mac-cu-src/SimulatorViews.swift) gates actual capture behind `validationOnly` and the named fixture policy; general `simulatorViews` returns unavailable. [`SimulatorToolbox.swift`](../../mac-computer-use/skills/mac-computer-use/scripts/mac-cu-src/SimulatorToolbox.swift) disables its view hierarchy UI. Do not route fixed-coordinate polygons into the AX rectangle rotation path. Device viewport, orientation, letterboxing, backing scale, clipping, screenshot time and host rendering each need their own verified conversion.
- The existing private worker uses the selected Xcode's LLDB/debugserver, one target attach and a verified main queue/thread; it uses bounded evaluation, exception trapping, no all-thread fallback, detach, and same-process running/untraced recovery checks. Preflight and attach are not atomic. Evaluation runs target code and may have side effects even on a read. A timeout, process exit, failed detach or failed child cleanup is not success and must not publish a fresh hierarchy. Preserve the exact identity `(device ID, PID, process start, executable path, captureID)` and no arbitrary caller-supplied expressions/commands. Details and existing limits are in [capture documentation](../simulator-view-capture.md).

### Installed Xcode observations, not supported API

Static `nm`/`strings` of `/Applications/Xcode.app/Contents/SharedFrameworks/DebugHierarchyFoundation.framework/Versions/A/DebugHierarchyFoundation` shows exported `DBGTargetHub`, `DebugHierarchyPropertyAction`, request executor classes and request key symbols, plus selectors `sharedHub` and `performRequestWithRequestInBase64:`. `DebugHierarchyKit.framework/Versions/A/DebugHierarchyKit` contains the exact expression template `(id)[[(Class)objc_getClass("DBGTargetHub") sharedHub] performRequestWithRequestInBase64:@"%@"]`, as well as a distinct `DebugHierarchyTargetHub` in-place request template. This supports the **expression's provenance**, not the exact JSON request's provenance, wire compatibility, or call success. The repository calls it the original request but does not identify a reproducible upstream source for this particular dictionary. A historical public [crash stack](https://github.com/jezzmemo/JJException/issues/69) shows a 2019 chain from hub to target hub, request executor and property action; it is corroborating historical evidence, not current behavior or an official specification.

The same Xcode `DebugHierarchyKit` binary contains `DBGSnapshot`, `DBGSnapshotNode`, `DBGImage`, `DBGSnapshotAssetManager`, `RequestFactory`, `_requestForEncodedLayersWithSnapshot:`, `_requestForRenderedViewsWithSnapshot:`, `_requestForRenderedEffectViewsWithSnapshot:`, `_requestForRenderedMultiLayerViewsWithSnapshot:`, and strings `encodedPresentationLayer`, `snapshotImage`, `snapshotImageRenderedUsingDrawHierarchyInRect`, `visualRepresentation`, `masksToBounds`, `sublayerTransform`, `transform`, `zPosition`, constraint property names. These names suggest distinct lazy requests and representation types. They do not identify complete request payloads, response schemas, fidelity, capability, write support, or redistribution rights. Both host frameworks report bundle short version 1.0/build 2; arm64 Mach-O UUIDs are `BD40A994-CE92-3712-AADD-7E933A3D7273` (Kit) and `0267FA46-B667-3A1C-A1A8-A1CA8BF48F8D` (Foundation). Host Mac debugger support dylib statically links Foundation by install name; this is not proof of simulator runtime linkage. The selected iPhoneSimulator SDK has a `libViewDebuggerSupport.tbd` declaring `/usr/lib/libViewDebuggerSupport.dylib` for arm64/x86_64 simulator. A stub is not evidence of the installed guest runtime image, its version, or successful loading.

| Frame, bounds, 2D transform, visibility | Public [`UIView`](https://developer.apple.com/documentation/uikit/uiview) properties; current private request names them | Frame is superview-relative; rotated transforms, ancestor clipping and effective alpha are not computed by the parser. Presence/absence varies by response. |
| Constraint relationships | Apple Xcode size inspector; request asks for items, attributes, multiplier, constant, relation, priority, active | Raw values may exist; parser does not build a verified constraint graph or associate every constraint with the selected view. | Layer 3D transform, `zPosition`, masks | Xcode binary strings only for these request names | Current request/parser does not establish values or presentation-tree timing. Physical transform Z, layer `zPosition`, sibling ordering and artificial exploded depth are distinct. `clipsToBounds` is not an arbitrary mask or a visible-polygon proof. |

## Candidate product contract

**Target and view.** Explicitly claim one booted Simulator/device and current front app, show app/device and capture time, and let the user select a window/scene when multiple are available. Do not attach merely on selection. Capture on explicit action; reject device/front-app/lifetime changes, existing debugger, inaccessible target, bad schema and cleanup uncertainty with distinct actionable states. No fallback to another app/window. A linked separate native window limits changes to the existing LCD/input pipeline: tree, 3D canvas and inspector share one immutable capture; selection and camera gestures act only on host UI. Explicit close/cancel tears down only owned work. Keep host keyboard/pointer ownership and guest HID routing distinct; no simulated guest input from selection.

Use a perspective camera with textured quads where the individual texture and geometry are actually observed. Keep tree order and sibling order explicit and label exploded spacing as a visualization parameter. Represent unavailable texture with a clearly marked outline, not a fabricated image. Show a separately timestamped composited screenshot only as reference; comparing its pixels with a reconstruction requires equivalent orientation, scale, clipping, blend/effects and timing. Separate view, layer and declarative SwiftUI scopes. [SceneKit's `SCNPlane` is currently deprecated](https://developer.apple.com/documentation/scenekit/scnplane); a small Metal-backed native canvas is a viable candidate, but renderer choice and minimum OS need design review, not a claim of validated implementation.

**Typed mutation.** Offer only one explicit property change at a time, initially `hidden: Bool` and finite `alpha` in `0...1`; later a well-defined explicit sRGB RGBA color or nil may be considered only with truthful old-value representation. Dynamic, pattern, extended-gamut and otherwise non-round-trippable colors must be rejected, not silently flattened. Apple specifies [alpha range and ancestor effects](https://developer.apple.com/documentation/uikit/uiview/alpha), and main-thread UI access in its UIView documentation. Do not expose selectors, arbitrary Objective-C, LLDB, shell, address entry, KVC keys or free-form code. Avoid constraints/frame/transform editing until ownership, layout reapplication, transform/animation semantics and postconditions have independent proof. A setter can be overridden and cause arbitrary app work, layout, or irreversible effects; a typed allowlist limits input, not side effects.

A proposed operation is an internal fixed-template LLDB expression on the uniquely verified main thread, once debugger access and identity requirements are proven: validate device, front app, PID/start/path and selected window; locate the exact live selected object using a robust capture-scoped identity; verify object is a currently reachable `UIView`, expected parent/window and operation capability; read the original typed value, compare to the expected captured/current value, apply exactly one setter, then read back. Serialize a bounded result with old/requested/observed values and operation ID. A later fresh capture and, separately, a rendered frame can show whether the visual result persisted; successful setter/readback alone proves neither rendered pixels nor application state stability. A single setter can still partially take effect or throw after side effects; report `not_applied` only when established, otherwise `outcome_uncertain`. Never automatically retry an uncertain mutation.

**Lifetime blocker.** Addresses are not persistent object IDs: even in the same PID/start/path, an old object can deallocate and its address be reused by a different same-class object in the same parent position. Re-traversal, fresh geometry, timestamp, class and value checks alone cannot prove identity. Investigate either (a) a bounded, user-visible stopped inspection transaction that retains the actual selected object and edits it before resuming, with strict deadlines and full cleanup, or (b) a target-side capture-scoped weak object registry plus unforgeable generation token whose zeroing/lifetime behavior is verified, without holding objects alive indefinitely. Both add invasive target-side state and require experiments; do not dereference an old raw address or enable edit until a mechanism is proven. A registry may itself allocate, affect lifetime or fail with deallocation races. An attach/stop on behalf of the user is disruptive and may not be viable for an interactive session.

An undo record is valid only while the same object token and process lifetime remain valid, and only if its current typed value still equals the applied value; otherwise refuse to overwrite the app's later changes. Restoration is another explicit typed edit and can fail or trigger side effects. A process crash, timeout, cancellation, detach failure, target exit or lost identity invalidates the record; never promise rollback. Same-target detach/recovery and child reaping are independent of whether an edit applied. Report `cleanupFailed` or `outcome_uncertain` as appropriate, avoid target signalling or blind retries, and preserve evidence. App code, layout, animation and SwiftUI reconciliation can immediately overwrite runtime values. All edits are transient target-memory changes, not persisted source/project edits.

## Staged experiments and go/no-go gates

These are future work, not actions taken in this research stage. Keep the existing fixture/general-app/overlay gates closed until each relevant evidence boundary is met. Follow [native check safety](../native-check-safety.md), device claim, single foreground owner, exact executable budget, parent watchdog, input guards, cleanup and restoration. Record Xcode, host OS, simulator runtime/device, target identity, signing/debuggability, time and source revision.

1. **Headless contracts:** validate strict schemas, property allowlist/ranges, pointer reuse/replaced-node rejection, stale device/window/capture, uncertain outcome/no retry, timeout/detach/recovery, no arbitrary-expression entry and ownership. Simulate setter side effects, mismatched old/readback, non-round-trippable colors and undo conflicts. Native dispatch and watchdog guards precede GUI.
2. **Owned fixture, read:** on one claimed device, measure parent/sibling ordering, multiple scenes/windows, hidden/alpha, scrolling, nested transforms, clipping/masks, constraints and SwiftUI hosting. Compare target-side oracle with collector data, then capture a separately timed simulator image. Confirm crash, competing debugger, cancellation and timeout handling with owned fixtures. Do not promote fixture success to general support.
3. **Texture feasibility:** in a disposable debug app, separately investigate private rendered/encoded request serialization and public app-owned rendering. Determine per-node vs subtree inclusion, resolution, pixel format, crop, effects, clipping and read-time side effects; no automatic hide/unhide. Exercise blur, transparency, shadows, video/Metal, animation, system overlays and protected/missing surfaces. Reject or visibly mark unavailable representations. Capture time ranges and size limits; measure overhead and recovery.
4. **3D and alignment:** use known colored/overlapping shapes and independent target oracle. Verify depth ordering and picking, rotation/zoom, zero-explosion composite, screenshot pixel correspondence at scales/orientations/letterboxing, and LCD host transform separately. Test parent masks, layer transforms and moving content; distinguish observed transform from synthetic depth and model/presentation values. A rendered host window, not JSON geometry or screenshots alone, is the acceptance evidence.
5. **Identity and edit:** use an owned fixture that deallocates/recreates same-class views at reused addresses, changes parent and original values, overrides setters, throws or exits. Prove identity mechanism across capture, resume and edit; exercise main-thread `hidden`/`alpha`, before/after/readback, visible postcondition, conflicting undo and partial/timeout/detach recovery. Gate color and constraint/transform separately. Never broaden on address/class/parent agreement alone.
6. **General debuggable apps:** coordinate a small set of user-owned UIKit, mixed SwiftUI, multi-window and independently built debug apps without adding an SDK. Record unsupported/debugger-conflict/signing/runtime outcomes as such; assess Xcode/runtime combinations individually. Run full native checks and protected serial foreground checks before any eventual delivery. Local installation, live UI and source/build tests are separate evidence.

**Open questions for cross-review:** Can the private hierarchy and additional image requests be constructed without unstable reverse engineering or unwanted rendering side effects? Can a bounded target-side weak registry establish identity without retaining or modifying arbitrary apps in unacceptable ways? Can a composited reference and per-node render be synchronized closely enough under animation? Which runtimes and signing states actually allow attach, and can cleanup be established under every interrupted operation? Can an interactive stopped transaction preserve app usability? Until answered, keep unsupported results explicit and no production gate is justified.
