## Flow and ownership

The SwiftUI runner's explicit `--recording-transition` harness lane launches the initial fixture without env287. The default pre-recorded lane retains its existing launch. No fixture/session/restart fields enter production preparation argv or environment.

After a genuine initial capture, `live.swift` verifies the visible enabled production button, its controller and `prepareRecordingNow` selector, and the exact state-loss disclosure. It publishes capture/owner/inspection/epoch readiness. `recording_owner.Worker` pins the installed executable, plist, MCM metadata, data directories, native original target, boot and continuously held claim. It sends one atomic owned 0600 arm control using host wall time plus the remaining original host duration. Guest uptime is never compared with host CLOCK_MONOTONIC.

The worker reads the exact pending bytes and matching arm receipt, retaining their SHA256. An empty initial receipt means the fixture has not serviced the control. Recreated host arms refuse existing pending/claim/spent/consumed files. The parent acknowledges the same declaration before the worker permits the UI action. Permission publication is a conservative unknown-dispatch boundary: cancellation is no longer safe once another process may have consumed it.

The UI archives action provenance and calls that same visible enabled `NSButton.performClick(nil)`. This is AppKit action-path evidence, not a physical click or human acceptance. Existing input counters, focus checks and deadlines are unchanged. Opening, capturing, timers and worker ticks never invoke the recording button or a backend recording callback.

`ui_process_contract` binds exact `python -I capture.py --prepare-recording recording-request.json` argv, native parent/start/group, a private bounded request/result folder, immutable prepared resources and selected-Xcode setting, the strict production request, and the actual released ledger. Its compact operation records must join full request/wire/result receipts, owner/inspection/epoch, terminal release and debugger/child quiescence. The capture parser remains unchanged. Read-only admission uses the existing serial utility slot without requiring an intent marker. Preparation shares the capture supervisor slot and admits no worker/debugserver. Only the bound launch phase admits the exact argv-free simctl launch; reconciliation is allowed only after the observed launch child is independently absent. Existing wrapper hashes, forward exec topology and family/global limits remain in force.

`recording_owner.Owner` retains one `TargetCursor` across three-second observations. The old target must be independently absent through two ESRCH status reads and kill0, with an observed empty executable interval. Zombie, denied reads, PID reuse, extra instances or a missed gap refuse admission. Native double reads then bind the successor's PID/start/path/device/state, env287, original launchd parent and worker, unchanged boot, installation/MCM/data and consumed capsule/startup fields. The marker is intent only. Result, PID, oracle and capsule alone never grant capture authority.

A candidate can precede the helper result or the fixture's first new oracle. It remains custody only until the helper and launch settle, the successful result joins the candidate, the exact consumed bytes/startup receipt match, and the original host/arm deadline permits admission. Uncertain launch or UI loss cannot resume capture. The parent publishes revision 1 once, only after the complete native family, semantic roles, global budgets and final acceptance cutoff pass; the UI waits for it before switching its current PID and ledger. The observer and session cleanup consume the same owner binding. UI-produced identities are candidates only.

The old released ledger remains separate from the successor ledger. Collection archives each lifetime independently, including full receipts and retired release proofs. UI owner draining checks both histories. Session cleanup selects the currently admitted target, revalidates both released histories, installed resources, boot, original claim/deadline and exact retained helper/UI/launch absence. Unknown dispatch/custody preserves the installation and claim. Before-dispatch cancellation requires the matching receipt, burns the one-shot budget and removes only the exact owned control. Capsule, pending/consumed/spent bytes are archived before any later authorized fixture uninstall.
